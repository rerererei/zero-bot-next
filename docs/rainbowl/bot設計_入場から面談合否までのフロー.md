# Bot設計：入場〜面談合否判定フロー

> 対象範囲：ユーザーがサーバーに入場してから、面談の合否が確定するまで。
> 合格後の規約同意・本プロフィール作成・相性診断用心理テストは、`rainbowl_server_handover.md` 7章の基本フローに既存の記載があるため、本ファイルでは扱わない。
> 前提となる決定事項（面接用プロフィール10項目など）は `channel_texts/面談手続き_面接用プロフィール項目.md` および本体資料19章を参照。
> ※プロフィールの提出先は、本人専用チャンネル（旧称：面談日調整、実際のチャンネル名は「表示名さん（DiscordID）」）に変更した。「プロフィール提出」「テンプレート置き場」の共有チャンネルはどちらも廃止済み。テンプレート本文は `channel_texts/面談手続き_面接用プロフィールテンプレート.md` を正本として管理し、Botはこれを本人専用チャンネルへ投稿する。

## 1. 全体フロー図

```text
入場
↓
Botが入場回数を記録し、前回挑戦（あれば）を履歴へアーカイブ（詳細9章）
↓
Botが運営向け「入場者詳細」チャンネルへ、ユーザー情報・入場回数・前回の審査状況をEmbedで投稿
↓
Botが入会案内カテゴリーの権限（入場者ロール：カテゴリーdeny／ようこそのみallow）をべき等にチェック・設定（詳細8章）
↓
Botが「入場者」ロールを付与（デフォルトで見えるのは「# ようこそ」のみ）
↓
本人が各チャンネル末尾の「次へ」を押すたびに、Botが次のチャンネルをその人だけに個別開放
（1ページずつ順番に閲覧。詳細は8章）
↓
本人が「入会申請」チャンネルの申請ボタンを押す
↓
Botが以下を自動実行
 ├─ ロールを「入場者」→「申請中」に変更
 └─ 面談・手続きカテゴリーに本人専用チャンネル「表示名さん（DiscordID）」を生成（本人＋運営のみ閲覧）
      ※このチャンネルが従来の「面談日調整」チャンネルにあたる。チャンネル名に表示名だけでなくDiscordIDも含めることで、
      　表示名が重複する応募者がいても運営が個別に見分けられ、チャンネル名の重複も避けられる
↓
Botが生成直後のチャンネルへ2通に分けて投稿
 ├─ 1通目：今後の流れの説明（案内文）
 └─ 2通目：面接用プロフィールのテンプレートのみ（コピペしやすいよう、他の文章を混ぜない）
↓
本人がテンプレートをコピーし、同じチャンネルへ必要事項を記入して投稿
↓
Botがその投稿（＝面接用プロフィール）に固定の「受付」スタンプ `<:uketsuke:1535212269472849971>`（リアクション）を設置
↓
運営が内容を確認
↓
├─ 内容に不備・虚偽の疑いがある → 同じチャンネル内で本人とやり取り（差し戻し、完全手動。ステータスはPROFILE_SUBMITTEDのまま）
│
└─ 問題なし → 運営が同じ「受付」スタンプを押す
    ↓
   Botがそのリアクションを検知し、「応募者プロフ置き場」チャンネルへ
   「@面談者（メンション）＋プロフィール全文」の形式で転記
    ↓
   運営が本人専用チャンネルで面談日程を調整
    ↓
   面談実施（VCまたはテキスト）
    ↓
   （任意）対応した運営が「面談記録」チャンネルへ手書きでメモを投稿。Bot処理なし、自由記述、あとから編集可能
    ↓
   運営が本人専用チャンネルで `/ok`（合格）または `/ng`（不合格）コマンドを実行する（運営ロールのみ実行可）
    ↓
   Botがコマンド種別に応じたモーダルを表示
    ├─ /ok → コメント入力欄（任意）
    └─ /ng → 理由入力欄（必須）
    ↓
   運営がモーダルへ入力し、送信ボタンを押す
    ↓
   ├─ /ng送信 → 本人への通知なし（無連絡）。Botが自動キック、合否記録チャンネルへ「ユーザー名・ユーザーID・アイコン・理由」を赤の左線Embedで保存
   │            ※無連絡キックの可能性があることは、Botではなく面談時に運営が口頭で説明する
   │
   └─ /ok送信 → ロールを「申請中」→「合格」に変更
              Botが規約・ルールカテゴリーを開放
              Botが合否記録チャンネルへ「ユーザー名・ユーザーID・アイコン・コメント」を緑の左線Embedで保存
              Botが「合格通知」チャンネルへ合格の旨を投稿（本人への一次通知。本人専用チャンネルへは投稿しない）
              本人専用チャンネルを即時削除（不合格側と同じ。通知先を分けたことで削除前に読まれる心配がない）
              （以降は本体資料7章の基本フローへ合流）
```

## 2. 状態管理（ステータス）

Bot内部で応募者ごとに保持する想定のステータス。

```text
NOT_APPLIED        入場済み・入場者
APPLIED            申請ボタン押下済み・プロフィール未提出（3日超過で自動キック対象。7章参照）
PROFILE_SUBMITTED  プロフィール提出済み・運営の「受付」スタンプ待ち（内容に不備がある場合の差し戻し中もこのまま。7章参照）
SCHEDULING         面談日程調整中
INTERVIEW_DONE     面談実施済み・合否判定待ち
PASSED             合格
REJECTED           不合格（キック済み。手動`/ng`・自動キックのどちらもこのステータスにする）
WITHDRAWN          本人都合による辞退
```

`NEEDS_FOLLOWUP`は使わないことに決定したため削除した。内容確認で不備があった場合も`PROFILE_SUBMITTED`のまま扱う（7章参照）。

ギルドID＋ユーザーIDで一意に管理し、月次バッチ（12章）と同様にDynamoDB等での状態保存を想定。

レコードは不合格・辞退後も**削除しない**。再入場のたびに前回挑戦の状態を履歴（`application_history`）へ積み上げ、入場回数・前回の審査状況を運営が振り返れるようにする（詳細9章）。

## 4. ロール設計

- **入場者**：入場直後。ロールとしてはデフォルトで「# ようこそ」のみ閲覧可。残りの6チャンネルは「次へ」操作に応じてユーザー単位で個別開放する（8章）。
- **申請中**：申請ボタン押下後〜合否確定前。自分専用チャンネル（旧称：面談日調整）の閲覧権限を持つ。他の応募者の専用チャンネルは見えない。
- **合格**：合格直後〜規約同意ボタン押下前。規約・ルールカテゴリーのみ追加開放。
- **正式メンバー**：規約同意後（7章の基本フローに合流）。

ロールは基本的に1人1つ、上記の順にのみ遷移する想定。差し戻し（不備があった場合に「申請中」へ戻す等）は運営が手動で行う。

## 6. 通知設計

- **承認の合図**：プロフィール投稿を検知した時点で、Botがその投稿へ固定の「受付」スタンプ `<:uketsuke:1535212269472849971>`（リアクション）を設置する。運営はこのスタンプを見て「未承認の投稿がある」ことに気づき、内容確認後に自分でも同じスタンプを押すことで承認する。
- **応募者プロフ置き場への転記**：運営が「受付」スタンプを押した時点で、Botがプロフィール内容を「@面談者（メンション）＋プロフィール全文」の形式で「応募者プロフ置き場」チャンネルへ転記する（提出時点ではなく、承認後に転記する点に注意）。
- **合否結果の確定と記録**：`/ok` `/ng` 実行後にBotが表示するモーダル（コメント／理由）を運営が送信した時点で確定する。結果とコメント・理由は合否記録チャンネルへEmbedで記録する（合格＝緑の左線、ユーザー名・ユーザーID・アイコン・コメント／不合格＝赤の左線、ユーザー名・ユーザーID・アイコン・理由）。
- **本人への通知**：合格の場合のみ、「合格通知」チャンネル（規約・ルールカテゴリー側、既存ID `1534967599614398524`）へ合格の旨をBotが投稿する（DMは本人が受信拒否設定にしている場合に届かないため使わない、過去の指摘と同じ理由）。本人専用チャンネルは合否確定と同時に即時削除するため、本人専用チャンネルへは投稿しない。不合格の場合は本人への通知を一切行わず、無連絡のままキックする。無連絡でキックとなる可能性があることは、Botの案内文ではなく面談時に運営が口頭で説明する。
- **プロフィール未提出者の自動処理**：リマインドは作らず、代わりに申請（`APPLIED`）から3日経ってもプロフィール未提出のユーザーは日次バッチで自動キックする（7章参照）。日程調整（`SCHEDULING`）段階の停滞に対するリマインドは作らない。
- **入場時の運営向け通知**：`on_member_join`のたびに、「入場者詳細」チャンネルへユーザー情報（表示名・@handle・数値ID・アイコン・bio・アカウント作成日・アカウント年数）と、入場回数・前回の審査進捗・前回面談結果（合否・理由）をEmbedで投稿する（詳細9章）。再入場者を運営が一目で把握できるようにする目的。

## 7. エラー・重複防止

- 申請ボタンの二重押下で本人専用チャンネルが重複生成されないよう、ステータスが`NOT_APPLIED`の場合のみボタンを有効にする。
- 本人専用チャンネル内で本人が送った最初の投稿を面接用プロフィールとして扱う。内容の修正は新規投稿ではなく編集で行う想定（既存方針を踏襲）。それ以降の投稿は通常のやり取りとして扱い、リアクションの対象にはしない。
- 承認リアクションは、運営ロールを持つユーザーが押した場合のみ有効とする（本人が誤って自分のリアクションを重ねても承認扱いにしない）。
- 複数の運営が同時にリアクションを押しても、転記処理は一度しか実行しない（ステータスが`PROFILE_SUBMITTED`の場合のみ転記処理を行い、実行後は`INTERVIEW_DONE`系のステータスへ更新して以降のリアクション追加を無視する）。
- 不合格キック処理の直前に最新ステータスを再取得し、運営が先に「合格」処理をしていた場合は不合格処理を中断する（月次バッチの冪等性方針と同様の考え方）。
- **プロフィール未提出の自動キック（3日ルール）**：`APPLIED`のまま`applied_at`から3日経過し、かつ`profile_message_id`が未登録のユーザーを、日次バッチで自動キックする。挙動は`/ng`と同様（status = REJECTED、verdict_reasonに自動キックである旨を保存、本人専用チャンネルを即時削除）。キック直前に最新ステータスを再取得し、既に`PROFILE_SUBMITTED`以降へ進んでいる場合は対象から除外する（月次バッチと同様の冪等性）。バッチの実行基盤は本フロー専用に作らず、Bot全体で日次実行したい他の処理とまとめて実装する（常駐Bot内の`tasks.loop`で完結させる方針。12章参照）。
- **内容確認の差し戻し**：不備がある場合は運営が本人専用チャンネルで直接やり取りする完全手動対応とし、Bot処理は挟まない。ステータスは`PROFILE_SUBMITTED`のまま変更しない。本人が投稿を編集し、運営が再確認して問題なければ、通常どおり同じ「受付」スタンプを押して承認する（差し戻し回数の上限や専用ステータスは設けない）。

## 8. 入会案内カテゴリーの段階開放設計

7つの入会案内チャンネルを、「次へ」ボタンを押した順に1つずつ開放する。ロールを段階分作るのではなく、ユーザー単位のチャンネル権限オーバーライドで実現する。

### 権限の初期状態

- 「入場者」ロールに対して、入会案内カテゴリーはロール単位ではデフォルト非表示（`view_channel: deny`）にする。
- 「# ようこそ」チャンネルだけ、チャンネル単位で「入場者」ロールに `view_channel: allow` を上書きする。
- 残り6チャンネル（30秒でわかる概要〜入会申請）は、ロールとしては非表示のままにしておく。

この初期権限は**Botが`on_member_join`のたびに設定する**（Discord側での事前手動設定には依存しない）。具体的には、入場処理の一環として以下をべき等にチェック・設定する。

1. `onboarding_category_id`に対する「入場者」ロールの`view_channel`オーバーライドが`deny`でなければ、`deny`に設定する。
2. `CH_ONBOARDING[0]`（ようこそ）に対する「入場者」ロールの`view_channel`オーバーライドが`allow`でなければ、`allow`に設定する。
3. 既に正しい状態であれば何もしない（毎回の入場でDiscord APIを無駄に呼ばないため）。

これにより、この機能を有効化する際にDiscord側で事前に手動設定しておく必要がなくなる。すでに手動設定済みのサーバーでも、Botのチェックは「既に正しい」と判断してAPI呼び出しをスキップするだけなので無害。

### 進行の仕組み

1. 「# 入会申請」を除く6チャンネルの末尾に「次へ」ボタンを設置する。
2. 本人が「次へ」を押すと、Botが次のチャンネルに対して、押した本人のユーザーIDだけに `view_channel: allow` のオーバーライドを追加する。
3. 同時に、Bot内部の進捗ステータス（例：`onboarding_step = 2`）を更新する。
4. 本人だけが次のチャンネルを閲覧できるようになる。他の入場者ユーザーには影響しない。

### 進捗ステータス管理

```text
onboarding_step: 1〜7の整数（現在閲覧可能な最終チャンネル）
```

ギルドID＋ユーザーIDで一意に管理する。「次へ」ボタンの二重押下や、閉じたタブ・キャッシュされた古いボタンからの巻き戻り操作を防ぐため、押されたボタンが示すステップ番号が現在の`onboarding_step`と一致する場合のみ処理を進める（一致しない場合は何もしない）。月次バッチ（12章）と同様の冪等性の考え方を踏襲する。

### 権限の後片付け

「申請中」ロール（入会申請ボタン押下後に付与）には、ロール単位で入会案内カテゴリー全体を閲覧可能にしておく。「申請中」ロールを付与するタイミングで、Botはチャンネル2〜7に残っている本人向けの個別オーバーライドを削除する。個別オーバーライドを溜め込まないための後片付けであり、機能上必須ではないが、チャンネルごとの権限オーバーライド数（Discordの上限は1チャンネル500件）を圧迫しないために行う。

### 注意点

- チャンネルを見て「次へ」ボタンを押す操作は「View Channel」権限があれば行えるため、各チャンネルに「Send Messages」権限まで付与する必要はない。
- 「# 入会申請」チャンネルは、閲覧権限さえあれば申請ボタンを押せるため、他の6チャンネルと同じ扱いでよい。

## 9. 再入場・入場履歴の設計

不合格・辞退でサーバーを離れたユーザーが再度参加してきた際に、運営が「何回目の入場か」「前回どこまで進んだか」「前回の合否・理由」を一目で把握できるようにする。

### 記録するデータ

`zero_bot_rainbowl_applicants`に以下を保持する（ギルドID＋ユーザーIDで一意、レコードは削除しない）。

- `join_count`：`on_member_join`のたびに+1する累計入場回数
- `first_joined_at` / `last_joined_at`：初回・直近の入場日時
- `application_history`：過去の挑戦を1件ずつ積み上げた配列。各要素は「その挑戦をどこまで進めたか（`final_status`）」「合否とその理由（`verdict_reason`、判定がある場合のみ）」「入場日時・申請日時・アーカイブ日時」を持つ
- 現在進行中の挑戦分の`status`／`onboarding_step`／`applicant_channel_id`／`profile_message_id`／`applied_at`／`verdict_reason`（`/ok`・`/ng`実行時に理由・コメントを保存）

### 再入場時の処理順序

1. 既存レコードを取得する
2. 既存レコードがあれば、現在保持している「今回挑戦分」のフィールドをスナップショットとして`application_history`へ追記（アーカイブ）し、以下は挑戦のリセット対象とする：`status`／`onboarding_step`／`applicant_channel_id`／`profile_message_id`／`applied_at`／`verdict_reason`
3. `join_count`を+1、`last_joined_at`を更新（レコードが存在しない＝初回入場なら`first_joined_at`も設定し、履歴アーカイブは行わない）
4. 「入場者」ロールを付与
5. 「入場者詳細」チャンネルへEmbedを投稿（統計・直前のアーカイブ内容を使って構築）

初回入場（履歴なし）の場合は、Embed中の「前回の審査状況」「前回の合否」欄は「初回入場」のように表示する。

### 「入場者詳細」Embedに含める項目

| 項目 | 内容 |
|---|---|
| ユーザー名（表示名） | サーバー上の表示名 |
| ユーザー名（@handle） | Discordの新形式ユーザーネーム |
| ユーザーID（数値） | 内部の数値ID（スノーフレーク） |
| アイコン | プロフィール画像 |
| Discordの自己紹介文（bio） | 取得可否はBotトークンでの技術検証が必要（10章参照） |
| アカウント作成年月日／アカウント年数 | 数値IDから算出可能 |
| 何回目の入場か | `join_count` |
| 前回どこまで審査が進んだか | `application_history`最新要素の`final_status` |
| 前回面談をしていた場合の合否・理由 | `final_status`が`PASSED`/`REJECTED`のときのみ、`verdict_reason`もあわせて表示 |

### 確定事項（追記）

- 「受付」スタンプ：カスタム絵文字 `<:uketsuke:1535212269472849971>`
- 合否コマンド：`/ok`（合格）／`/ng`（不合格）。運営ロールのみ実行可
- `/ok` `/ng`とも実行直後にモーダルを表示し、送信をトリガーに確定処理（ロール変更／キック／Embed記録）を行う（`/ok`＝コメント任意、`/ng`＝理由必須）
- 合否記録Embedの左線色：合格＝緑、不合格＝赤
- 本人への通知は合格時のみ、「合格通知」チャンネル（ID `1534967599614398524`）へ投稿する。不合格は無連絡でキック。無連絡キックの可能性は面談時に運営が口頭で説明する（Botの案内文には反映しない）
- 本人専用チャンネルは合否問わず即時削除する（アーカイブは行わない）。合格の旨は本人専用チャンネルではなく「合格通知」チャンネルへ投稿することにしたため、削除前に本人が読めるかを気にする必要がなくなった
- `zero_bot_rainbowl_applicants`のレコードは削除しない（永続保存）。再入場のたびに前回挑戦を`application_history`へアーカイブし、`join_count`をインクリメントする（9章）
- 再入場のたびに「入場者詳細」チャンネル（ID `1534968774434750645`）へEmbedを投稿する（9章）
- 表示名がDiscordのチャンネル名制約で変換・除去される問題は事前対策をしない。実際に運用して困ってから対応する
- プロフィール未提出のまま申請から3日経過したユーザーは自動キックする（7章参照）。日程調整段階のリマインドは作らない

- `CATEGORY_ONBOARDING`（入会案内カテゴリー）の入場者ロールに対する初期権限は、Discord側の事前手動設定に依存せず、**Botが`on_member_join`のたびにべき等にチェック・設定する**（8章参照）
